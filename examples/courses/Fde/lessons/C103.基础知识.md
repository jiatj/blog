## 场景与目标

**AI 写好了，我还能自己改吗？** 这一课要做到：

- 我知道从哪个文件开始。
- 我能说清这次只改什么。
- 我能运行并检查结果。
- 我能让同学按记录复现。

> 把一次修改，做成完整的小闭环。

## A 基础：先读一小段代码

打开 C102 运行过的 check.cjs：

~~~javascript
const note = { title: "我的第一条笔记" };
console.log(note.title);
console.log("Node.js 可以运行课程代码");
~~~

> 指出：标题在哪里？哪一行把它显示出来？

说明：`note` 是一条示例数据，`title` 是标题字段，`console.log` 负责显示内容。如果之前已经改过标题，以你的实际文件为准。这里不展开完整的 JavaScript 语法体系——项目需要什么，我们再学什么。

## A 基础：做一处自己的修改

先确定自己的标题文本（这一步不要让 AI 替你决定），再给它一个能检查的小任务：

~~~text
把 check.cjs 的标题改成我自己的课程笔记名称。
先告诉我将修改哪里，只改这一项。
运行后首行显示新标题，第二行保持原样。
报告修改文件、执行命令和实际输出。
~~~

> 如果 AI 不能直接运行命令，就自己在终端执行 `node check.cjs` 并核对结果，在记录里标明「人工执行」。完成后用 VS Code 打开实际文件，确认修改真的写进了文件——不能只看聊天里的代码块。

## A 基础：把结果留下来

新建 practice.md，写一份可以复验的修改记录：

~~~markdown
# 我的第一次修改
## 目标
把笔记标题改为我自己的名称。
## 实际修改
记录修改文件、修改位置与新标题。
## 验证
记录实际命令、输出和仍未验证的部分。
~~~

记录要求：

- 命令使用带语言标记的代码块；运行输出单独标注，不混进命令块。
- 已有 practice.md 时，在文件末尾追加本次记录，不覆盖上次的操作。
- 标明 AI 帮了什么、自己决定或验证了什么。

## A 基础：同伴验收

让同学按你的说明，再做一次：

1. 对方能找到文件和运行入口。
2. 对方能按命令看到相同类型的结果。
3. 你能解释改动目的与验证方法。

> 交付：修改文件 + 操作证据 + 简短个人总结。不同同学的标题可以不同，验收看「符合自己的目标」，不看文字是否一模一样。可以在自己电脑上现场演示，不需要分享整台电脑的权限。

## 回到贯穿项目

将同样的方法用于学习笔记本：

- 打开已运行的笔记本 V0。
- 选择一处小修改，例如页面标题或空状态文案。
- 检查新建、编辑、保存和刷新仍正常。
- 将结果补充到项目说明中。

> 还没有可运行的骨架时，这一项保持「待完成」——check.cjs 是练习，不能代替 V0 项目交付。这一轮不要加登录、多人协同或模型调用；V0 的要求是：AI 服务不可用时，基本记笔记功能仍然可用。

## B 提高：独立处理一个变化

从照着做，到自己找入口：

- VS Code：完成一次行号定位与错误修复。
- WorkBuddy：提交包含复现步骤的报错任务。
- Markdown：记录原因、修复和再次运行结果。

> 预期：别人能够照你的记录复现并验证。选择一条线完成即可，不要求把三项全做完。

## C 高级：为后面的课程留下方法

能力增长，检查也要跟着增长：

- 数据库阶段：追踪保存与读取，保护旧笔记。
- RAG 阶段：区分检索证据与生成答案。
- 工具调用阶段：确认实际执行结果。
- 交付阶段：按说明运行，检查失败与恢复。

> C 的目标是判断与复验，不是追求更多技术名词。

## 收尾与下一步

今天学会的，是一种工作方式：

~~~text
明确目标 → 找到文件 → 做一处修改
运行检查 → 记录证据 → 带着问题继续迭代
~~~

- 下次带来一项自己提出的小需求。
- 环境出问题先回 [C102 开发环境](./C102.开发环境.md)；需要版本保护时，再学习 Git 的提交与恢复。
